# 0001: Live hardware data through an aggregated API

- Status: Proposed
- Authors: @aireet
- Created: 2026-10-05

## Summary

Serve live sensor readings and System Event Log entries through a Kubernetes aggregated API
(`live.bmc.kube-bmc.io`), implemented by the kube-bmc server and backed by the node agents'
in-memory snapshots. The data is never stored in etcd. This follows the pattern of
`metrics.k8s.io`, served by metrics-server.

## Motivation

kube-bmc keeps fast-changing data out of etcd: the `BMC` status holds a summary that is written
only on meaningful changes, and agents renew a small Lease for liveness. Full sensor lists and SEL
entries are served by each agent over HTTP.

Today, clients reach that data in two different ways:

- the dashboard and MCP endpoint go through the kube-bmc server;
- `kubectl bmc` uses the API server's pod proxy to reach the agents.

An aggregated API gives all Kubernetes clients one resource for live data, without storing it.

### Goals

- `kubectl get bmcsensors <node>` and `kubectl get bmcevents <node>` return live data.
- No writes to etcd.
- The kube-bmc server remains optional for read-only use of `BMC` objects.

### Non-goals

- Historical data. Prometheus remains the store for time series.
- Watch support. Live data is polled.

## Proposal

The kube-bmc server registers an `APIService` for `v1alpha1.live.bmc.kube-bmc.io` and serves
two read-only, cluster-scoped resources named after the node:

| Resource | Content |
|---|---|
| `bmcsensors` | All sensors with readings, state and thresholds |
| `bmcevents` | Newest SEL entries and SEL usage |

The server implements the aggregated API with `k8s.io/apiserver`, which provides delegated
authentication (front-proxy client certificates, TokenReview) and delegated authorization
(SubjectAccessReview), discovery, OpenAPI and table output for `kubectl get`. Requests are
answered from the agent snapshot, as `/api/v1/bmcs/{name}/live` is today.

The Helm chart gains `liveAPI.enabled` (default `false` until the API graduates). TLS uses a
certificate generated by cert-manager when available, otherwise a self-signed certificate with
`insecureSkipTLSVerify`, as metrics-server does by default.

`kubectl bmc sensors` and `events` use the aggregated API when it is available and fall back to
the pod proxy otherwise.

## Alternatives considered

- **Store sensors in the `BMC` status.** Rejected: hundreds of readings per node changing every
  30 seconds would dominate etcd write traffic.
- **A separate etcd for kube-bmc resources (`--etcd-servers-overrides`).** Rejected: it requires
  changing the API server configuration, which managed Kubernetes services do not allow, and
  adds a stateful component to operate.
- **Keep the pod proxy.** Works today for kubectl-bmc, but is not usable by generic Kubernetes
  clients such as `kubectl get`.

## Compatibility and migration

The new API group is additive. The pod-proxy path remains supported until the aggregated API
reaches beta.

## Security considerations

- The aggregated API server only accepts requests authenticated by the API server's front proxy,
  verified with the `requestheader-client-ca-file` from `kube-system/extension-apiserver-authentication`.
- The server gains read access to that ConfigMap and the `system:auth-delegator` role, as
  metrics-server does.

## Test plan

- Unit tests for the REST storage (get, list, table conversion, not-found).
- An end-to-end test in kind with an `APIService`, verifying `kubectl get` output.
